6 · 주제별 가이드

세 주제, 같은 골격

세 주제는 모두 「센서 → 상태 추정 → 제어 → 구동」 루프입니다. 다른 것은 좌표 · 지표 · 안전 · 함정입니다. 공통 단계를 먼저 보고, 자기 주제의 절을 읽습니다. 각 절의 내용은 starter 의 topics/ 파일에도 들어 있으니, 그 파일을 AGENTS.md §8 에 붙여 넣습니다.

§1공통 단계

한 단계가 대략 세션 1~3 개입니다. 단계마다 끝나는 조건이 있고, 그 조건은 로그나 시험으로 확인합니다.

단계할 일끝나는 조건
1센서 하나를 읽어 CSV 로그로 남깁니다check_log.py PASS, 샘플률 실측값 기록
2구동기를 열린 루프로 움직입니다 (낮은 한계)「+ 명령 → + 방향」 확인, hw/limits.py 값의 출처 기록
3raw → 물리량 변환과 보정을 한 모듈에 만듭니다전 범위 스윕 테스트 통과, 보정값 파일 커밋
4smoke 시험을 만듭니다전제 검사 (설정 로드 · tick > 0 · 명령 변화 · 외란 시 FAIL) 포함
5첫 폐루프 — 낮은 이득, 좁은 한계학생 입회 실행, 로그 PASS, 회의록에 관찰 기록
6baseline 측정재현 가능한 외란 · 목표로 n ≥ 3, mean ± sd
7개선 — 한 번에 하나씩사전등재 → 탐색 1 회 → (유의미하면) 확증 3 회
8시연 조건 고정과 보고서대표 수치 2~3 개 확정, 모든 수치가 로그로 거슬러 감

시뮬레이터가 있으면 6~7 단계의 탐색을 시뮬레이터에서 먼저 하고, 실물에서는 확증만 합니다. 단, 시뮬레이터를 믿기 전에 같은 이득에서 실물과 시뮬레이터의 계단응답을 먼저 비교합니다 — 이 비교가 탐색 앞에 와야 합니다 (사례 Day 4).

Kiro Specs 로 단계 시작하기

3 · 4 단계처럼 코드 구조가 생기는 단계는 spec 으로 시작하면 계획이 파일로 남습니다. 요구사항은 측정 가능한 문장으로 씁니다.

WHEN the raw distance reading spans the full sensor range in 1 mm steps
THE SYSTEM SHALL convert every reading through the single calibration module
AND the safety limit check SHALL use the same converted value as the control loop

WHEN any converted value falls outside the calibrated range
THE SYSTEM SHALL clamp the servo command to neutral and log a range event

§22D ball balancing

루프: 공 위치 (카메라 또는 저항막 터치패널) → x · y 두 축의 제어 → 서보 2 개로 플레이트 기울기.

좌표 · 단위
플레이트 좌표 (x, y) [mm], 원점은 중심입니다. 축 방향은 그림 하나로 고정합니다. 카메라 픽셀 → mm 는 homography 보정값을 파일로 커밋합니다. 서보 각 → 플레이트 기울기는 링키지 때문에 비선형입니다
지표
정상상태 오차 RMS [mm] · 정착시간 [s] (기준 원 반지름을 고정) · 외란 복귀시간 [s] · 원 궤적 추종 오차 RMS [mm] · 루프 주기 실측
안전
서보 각도 한계는 링키지가 걸리는 각보다 작게 둡니다. 한계에 붙어 떨면 (stall) 전류가 커지므로, 일정 시간 이상 한계에 머물면 중립으로 돌리는 감시를 둡니다

흔한 함정

  • 카메라 자동 노출 · 자동 화이트밸런스 — 런마다 검출 임계가 달라집니다. 고정하고 실제 값을 로그에 남깁니다.
  • x · y 축 부호나 서보 배선이 뒤바뀜 — 폐루프 전에 한 축씩 열린 루프로 방향을 확인합니다.
  • 소프트웨어 PWM 지터 — 하드웨어 PWM 이나 PWM 드라이버 보드를 쓰고, 지터를 측정해 기록합니다.
  • 목표 변경 시 미분 킥, 서보 포화 중 적분 누적 (windup).
  • 프레임 누락 · 처리 지연 — 프레임마다 타임스탬프를 남깁니다.
  • Pi 3 B+ / 4 의 처리 성능 — 해상도를 낮추고 (예: 320×240) 프레임당 처리 시간을 측정합니다.

로그 최소 필드: t, tick, x_mm, y_mm, ref_x, ref_y, u_x_deg, u_y_deg, frame_ms · 규칙 파일: topics/ball-2d.md

§3Two-wheel self-balancing robot

루프: IMU 기울기 · 엔코더 바퀴 속도 → 기울기 루프 (+ 속도 루프) → 모터 2 개.

좌표 · 단위
기울기 θ [deg] 는 앞으로 기울면 + 입니다. IMU 축 방향과 장착 오프셋 (똑바로 세웠을 때의 θ₀) 은 한 모듈에서 보정합니다. 바퀴 지름 · 기어비는 측정값과 출처를 적습니다
지표
정지 균형 시 기울기 RMS [deg] · 견디는 최대 밀기와 복귀시간 · 제자리 위치 drift · 루프 주기 실측 · 런마다 배터리 전압
안전
넘어짐 차단 (예: |θ| > 35° 이면 출력 0) 을 코드와 시험으로 확인합니다. 첫 실행은 바퀴를 띄우거나 끈으로 매단 상태에서 합니다. 리튬 배터리에는 저전압 차단을 두고, 바닥에서 주변을 비우고 실행합니다

흔한 함정

  • 배터리 전압이 떨어지면 같은 명령의 토크가 줄어 사실상 이득이 바뀝니다. 전압을 로그에 남기지 않으면 두 런을 비교할 수 없습니다.
  • 자이로 bias drift, 가속도계 진동 잡음 — 상보 필터 (또는 Kalman) 의 시정수를 측정으로 정합니다.
  • 모터 데드존 · 좌우 차이 — 「명령 대 속도」 곡선을 양쪽 모두 열린 루프로 측정해 둡니다.
  • 100 Hz 이상의 루프는 Linux 에서 지터가 크고, Pi 3 B+ 에서는 더 큽니다 — 최대 Δt 를 보고합니다.
  • I2C 읽기 실패를 조용히 이전 값으로 대신하지 않습니다 — 실패 횟수를 셉니다.
  • 기울기 루프와 속도 루프의 이득을 동시에 바꾸지 않습니다.

로그 최소 필드: t, tick, theta_deg, gyro_dps, wheel_l, wheel_r, u_l, u_r, vbat, i2c_err · 규칙 파일: topics/two-wheel.md

§4Vision tracking + laser pointing

루프: 카메라 영상 → 표적 검출 → 영상 오차 → pan · tilt 서보 2 개 → 레이저 점.

좌표 · 단위
영상 (u, v) [px], 표적 면 [mm], pan · tilt [deg] 를 씁니다. 세 좌표계의 그림 하나를 둡니다. px → 각도 변환과 카메라–레이저 오프셋 (시차) 보정은 한 모듈에만 둡니다
지표
추종 오차 RMS — 영상 [px] 과 표적 면 [mm] 둘 다 · 명중률 (반지름 r 안) · 영상 → 구동 지연 [ms] 실측 · 처리 FPS · 검출 실패 프레임 수
안전
아래 경고를 따릅니다

레이저과목 안전 공지가 허용한 모듈만 씁니다. 사람 · 눈높이 방향으로 조준하지 않고, 표적 뒤에 빛을 막는 판을 둡니다. 레이저 출력은 소프트웨어 interlock 뒤에 둡니다: 기본 OFF, 「표적 검출 + 조준 각이 작업 영역 안 + 사람이 arm 스위치를 켬」 일 때만 ON 입니다. 에이전트는 레이저를 켜는 명령을 실행하지 않습니다. 시험은 LED 로 먼저 합니다.

흔한 함정

  • 자동 노출 · 조명 변화로 색 임계가 무너집니다 — 노출 · 게인을 고정하고 실제 값을 로그에 남깁니다.
  • 카메라 버퍼의 오래된 프레임을 처리해 지연이 커집니다 — 최신 프레임만 쓰고 프레임 타임스탬프를 남깁니다.
  • 레이저 점 자체가 표적처럼 검출됩니다 — 검출에서 레이저 색을 빼거나, 레이저가 꺼진 프레임에서 검출합니다.
  • 지연을 FPS 로 추정하지 않습니다 — LED 점멸 같은 방법으로 직접 잽니다.
  • Pi 3 B+ / 4 에서는 처리 FPS 가 카메라 FPS 보다 낮아지기 쉽습니다 — 해상도를 낮추고 처리 시간을 측정합니다.
