8 · 회고 · 제출

혼자 한 프로젝트를 다시 읽기

이 과목의 기말 프로젝트는 개인 과제입니다. 결정도 검증도 혼자 해야 하므로, 기록이 곧 두 번째 눈이 됩니다. 이 페이지는 혼자 일할 때의 결정과 검증, 프로젝트 끝의 프롬프트 회고, AI 사용 기록, 제출 전 점검을 다룹니다.

§1결정은 학생이, 검증은 다른 경로로

  • 결정자는 학생 본인입니다. AGENTS.md §0 에 그렇게 적혀 있고, 에이전트가 「승인」 을 구할 때 그 승인은 학생의 것입니다. 에이전트의 권고는 「에이전트 권고」 로 따로 적습니다.
  • 지도교수 면담의 내용은 프롬프트로 들어갑니다. 「교수님이 면담에서 외란을 손으로 주지 말라고 하셨는데, 그러면 비교 방식을 어떻게 바꿔야 할까?」 처럼 에이전트에게 전하면, 그 프롬프트가 회의록에 남아 결정의 출처가 됩니다.
  • 검증은 작성한 세션과 다른 경로로 합니다 (AGENTS.md §5-8). 혼자 하는 프로젝트에서 쓸 수 있는 경로는 이렇습니다.
    • 새 세션을 열어 「이 표의 수치를 로그와 대조해 줘」 처럼 검토만 시킵니다 — 같은 대화 안에서 묻는 것보다 독립적입니다
    • 다른 도구 (예: Kiro 로 작성, Copilot 이나 Gemini CLI 로 검토) 를 씁니다
    • 사람이 직접 렌더된 결과 (PDF · 그림) 를 이전 판과 비교합니다
    • 지도교수 · 조교의 피드백을 받습니다
  • 노트북과 Pi 를 오갈 때는 반드시 push 합니다. Pi 에서 한 커밋을 노트북의 handoff 가 모르면 다음 세션이 틀린 전제로 시작합니다 (사례 Day 17).

§2프롬프트 회고

프로젝트가 끝나면 docs/retrospective.md 에 회고를 씁니다. 회고의 중심은 내 프롬프트입니다. 모든 회의록의 「프롬프트 기록」 을 다시 읽고, 논의를 어떻게 끌어갔는지 분석하고, 다음 프로젝트에서 바꿀 점을 도출합니다.

  1. 모읍니다. Obsidian 검색 ("프롬프트 기록") 이나 grep 으로 모든 회의록의 프롬프트 표를 모읍니다. starter 에 들어 있는 tools/prompt_stats.py 로 세션별 프롬프트 수 · 짧은 승인의 비율 · 질문 수를 같은 기준으로 셀 수 있습니다 (사례의 출력 예).
  2. 관점별로 표시합니다. 계획을 먼저 요구했는지, 근거를 물었는지, 승인에 조건을 붙였는지, 질문으로 방향을 바꿨는지, 에이전트의 가정을 잡아냈는지 (1. 개요 §2).
  3. 사례를 고릅니다. 논의를 끌어간 프롬프트 3 개와, 따라가기만 해서 나중에 문제가 된 프롬프트 3 개를 회의록 경로와 함께 인용합니다.
  4. 개선안을 씁니다. 「다음에는 측정 결과를 받으면 먼저 정합 축을 묻겠다」 처럼 행동으로 3~5 개를 씁니다. 회고 문서는 「~함」 체로 씁니다.

왜결과물은 프로젝트의 끝을 보여 주지만, 프롬프트는 과정을 보여 줍니다. 같은 결과에 도달했더라도 에이전트의 제안을 승인만 한 경우와 질문으로 방향을 바꾼 경우는 다음 프로젝트에서 전혀 다른 결과를 냅니다. 프롬프트가 원문 그대로 남아 있어야 이 차이를 사후에 분석할 수 있습니다. 지도교수도 같은 기록을 읽고 피드백합니다.

§3AI 사용과 학업 정직성

이 과목은 AI 코딩 에이전트 사용을 전제로 합니다. 요구하는 것은 사용하지 않는 것이 아니라 무엇을 맡겼고 무엇을 확인했는지 남기는 것입니다.

  • docs/ai-usage.md 는 필수입니다. 세션마다 한 줄. 「검토한 범위」 를 구체적으로 씁니다 (4. 세션 운영 §8).
  • 보고서에 AI 사용 고지를 둡니다. 이 표에서 요약해 만듭니다 — 어떤 도구로, 어느 부분을, 어떻게 확인했는지.
  • 설명할 수 없는 코드를 제출하지 않습니다. 에이전트가 쓴 코드라도 시연 때 직접 설명할 수 있어야 합니다.
  • 에이전트가 제시한 출처는 원문을 확인합니다. 데이터시트 값 · 문헌 인용은 원본에서 찾아 확인한 것만 씁니다. 「원본에 없다」 고 쓰기 전에도 원본을 엽니다 (§5-7).
  • 프롬프트 기록을 고쳐 쓰지 않습니다. 검토 때 빠진 프롬프트를 채우는 것은 괜찮지만, 이미 있는 프롬프트를 더 나아 보이게 바꾸지 않습니다. 대화 원본을 보관했다면 (4. 세션 운영 §4) 대조할 수 있습니다.
  • 커밋 trailer (Assisted-by:) 는 학생이 정합니다. 그 밖의 세부 기준은 강의 공지를 따릅니다.

§4제출 전 점검

평가 기준과 제출 형식은 강의 공지를 따릅니다. 아래는 저장소가 「과정이 남아 있는 상태」 인지 확인하는 목록입니다.

항목확인 방법
회의록세션마다 1 편 있고, 각 회의록의 「프롬프트 기록」 이 비어 있지 않습니다. 옮기지 못한 구간은 그렇다고 적혀 있습니다
docs/retrospective.md프롬프트 회고 (수치 · 사례 · 개선안) 가 있습니다
AGENTS.md §9 개정 이력각 개정에 계기 (사고 / 지시 / 기록 갱신) 와 회의록 경로가 있습니다
handoff.md마지막 상태가 기록되어 있고, 결정 항목에 결정자 · 시각이 있습니다
실험 기록보고서의 모든 비교에 사전등재가 있습니다. 무효 런과 「사전등재 실패」 가 지워지지 않고 남아 있습니다
로그보고서 수치의 로그가 저장소에 있고 check_log.py 결과가 실험 기록에 있습니다
보고서 수치대표 수치가 요약 · 서론 · 결과에서 같은 값입니다. 바꾼 수치를 grep 으로 전부 찾아 고쳤습니다
docs/ai-usage.md빈 세션이 없고, 검토 범위가 구체적입니다
비밀 정보git log -p 와 프롬프트 기록에 IP · 비밀번호 · 토큰이 없습니다
실행 방법README 의 명령만으로 다른 사람이 시뮬레이터 · 시험을 돌릴 수 있습니다

§5자주 묻는 질문

에이전트가 규칙을 지키지 않습니다

먼저 규칙이 적재되었는지 확인합니다 (양성 대조 질문). 적재되었는데도 어기면, 위반을 회의록에 「⚠ 사고 —」 로 남기고 프롬프트에서 해당 조항 번호를 직접 인용합니다 (「§2-3 에 따라 결과만 먼저 보고해 줘」). 같은 위반이 반복되면 규칙 문장을 늘리기보다 검사 도구 (스크립트 · hook) 로 바꿉니다.

에이전트가 쓴 회의록에 프롬프트가 빠져 있습니다

대화가 길어 앞부분이 요약된 경우가 많습니다. 빠진 프롬프트는 채팅 창이나 대화 원본에서 찾아 채우고, 채웠다는 사실을 docs/ai-usage.md 에 적습니다. 자주 빠진다면 세션을 더 짧게 끊습니다 — 한 주제가 끝날 때마다 /session-close 를 씁니다.

크레딧이 모자랍니다

한 주제가 끝나면 세션을 닫고 새로 엽니다 — 긴 대화일수록 매 요청이 비쌉니다. 큰 파일이나 로그 전체를 붙이지 말고 파일:행 과 요약을 줍니다. 「확정 (재론 불요)」 를 유지해 같은 논의를 반복하지 않습니다. 간단한 작업은 비용이 낮은 모델을 고릅니다.

회의록 검토에 시간이 너무 듭니다

회의록은 에이전트가 쓰므로, 학생은 검토 항목 다섯 가지만 봅니다. 60~120 행이면 충분합니다. 문서가 커밋의 대부분을 차지하기 시작하면 세션 단위를 다시 생각할 때입니다 — 그래도 프롬프트 기록과 결정 기록은 줄이지 않습니다.

에이전트가 틀린 것을 자신 있게 말합니다

답을 이미 아는 질문으로 시험하고 (양성 대조), 원본을 직접 열고, 새 세션이나 다른 도구로 다시 확인합니다. 같은 대화에서 같은 질문을 여러 번 하는 것은 확인이 아닙니다.

Pi 3 B+ 에서 에이전트를 직접 돌릴 수 있나요

권하지 않습니다. 메모리가 1 GB 라 에이전트 도구와 원격 편집 서버가 버거워합니다. 노트북에서 에이전트를 쓰고 Pi 에서는 git 과 SSH 로 실행만 합니다 (5. 실습 환경 §1).

Pi 에서 sudo 가 필요하다고 합니다

대부분은 사용자 그룹 (gpio i2c video) 으로 해결됩니다 (5. 실습 환경). 패키지 설치나 데몬 활성화처럼 정말 필요한 경우는 학생이 직접 실행합니다.
