3 · 규칙 파일

AGENTS.md — 내 작업 방식을 에이전트가 매번 읽게 하기

규칙 파일은 에이전트가 세션마다 자동으로 읽는 유일한 문서입니다. 그래서 짧아야 하고, 바뀌지 않는 원칙만 담아야 하며, 모든 조항이 「왜」 를 가져야 합니다. 이 페이지는 starter 의 AGENTS.md 를 절 단위로 읽고, 규칙을 키우는 방법을 설명합니다.

§1절 구성

절내용왜 이 자리에
머리말이 파일이 단일 원본이라는 것, 유래, 개정 방법에이전트가 다른 파일의 규칙을 같은 무게로 섞지 않게 합니다
§0 개요목표 · 장치 · 제어 주기 · 핵심 지표 · 일정 · 결정자에이전트가 판단할 때의 근거입니다. 결정자는 학생 본인이고, 에이전트는 결정자가 아닙니다
§1 세션시작 순서, 시각 실측, 종료 절차세션 경계에서 정보가 가장 많이 사라집니다
§2 작업 순환계획 먼저, 결과 먼저, 문서는 승인 후에이전트가 스스로 범위를 넓히는 것을 막습니다
§3 하드웨어 안전구동 명령은 사람 입회, 한계 이중화, sudo 최소화소프트웨어 실수가 물리적 손상이 되는 유일한 영역입니다
§4 측정baseline, 탐색→확증, 같은 입력, 실제 적용값, 로그 무결성, 시뮬레이터 복제틀린 비교는 틀린 결론을 그럴듯하게 만듭니다
§5 디버깅 · 시험첫 이상에서 멈춤, 시험의 전제, 변환 한 곳, 필드 단위 비교, 「없다」 의 판정, 정정 검증증상을 덮는 수정과 공허한 PASS 를 막습니다
§6 기록회의록 (프롬프트 기록 포함), handoff, AI 사용 기록, 실험 기록, 문체세션 밖에 남는 기억의 형식입니다
§7 Gitpull/push 시점, 커밋 메시지, 이력 재작성 금지노트북과 Pi 사이의 충돌과 기록 손실을 막습니다
§8 주제topics/ 에서 고른 주제별 규칙좌표 · 단위 · 지표 · 안전이 주제마다 다릅니다
§9 개정 이력r번호 · 날짜 · 계기 · 내용 · 회의록규칙마다 「왜 생겼나」 를 거슬러 갈 수 있게 합니다

§2핵심 조항과 그 이유

모든 조항을 옮기지는 않았습니다. 아래는 학생 프로젝트에서 특히 자주 어겨지는 조항입니다. 조항마다 붙은 칩은 사례 저장소에서 그 규칙이 생긴 날입니다.

§1-1

시작할 때 git 이력을 handoff 와 따로 확인합니다

handoff 는 그것을 쓴 세션이 아는 것만 담습니다. 전날 저녁 Pi 에서 한 커밋을 노트북에서 쓴 handoff 가 빠뜨리면, 다음 세션의 에이전트는 그 변경을 모른 채 일합니다.

사례 Day 17

§1-2

시각은 매번 date 로 읽습니다

에이전트는 현재 시각을 모릅니다. 그럴듯한 시각을 지어내 기록하고, 그 시각으로 남은 시간을 계산해 일정 판단을 그르칩니다.

사례 Day 22

§2-2

진단은 원인에서 멈춥니다

원인을 찾은 뒤의 추가 측정은 새 계획입니다. 곧 바뀔 구성에서 잰 값은 쓸모가 없고, 승인 없이 잰 결과는 다른 설명 속에 묻히기 쉽습니다.

사례 Day 4

§2-6

결정에는 결정자와 시각을 붙입니다

에이전트가 스스로 정한 것 (「보고서는 동결되었다」) 이 결정처럼 기록되면 다음 세션은 그것을 사실로 받아들입니다. 결정자가 없는 결정은 가정입니다.

사례 Day 22

§3-1

구동 명령은 사람 입회 하에

에이전트는 명령과 「정상이면 보일 동작 · 중단 기준」 까지만 냅니다. 실행은 장치 옆의 학생이 합니다. 에이전트는 공이 날아가는 것을 보지 못합니다.

과목 규칙

§3-4

sudo 로 실행하지 않습니다

sudo 는 HOME 과 환경을 바꿉니다. 내 설정 대신 기본값을 읽은 제어기가 아무 일도 하지 않는데 시험은 통과할 수 있습니다.

사례 Day 2

§4-3

같은 시간이 아니라 같은 입력으로 비교합니다

「각각 60 초 돌렸다」 는 같은 조건이 아닙니다. 한쪽이 중간에 공을 떨어뜨려 리셋되면 외란을 받은 횟수가 달라집니다. 같은 seed 의 외란을 같은 횟수만큼 주고 비교합니다.

사례 Day 9

§4-4

공통 조건은 변수 하나로, 실제 값은 로그로

비교하는 두 코드가 센서 설정을 각자 정하면 언젠가 한쪽만 바뀌고, 그 차이가 결론을 만듭니다. 그리고 「설정했다」 가 아니라 「적용되었다」 를 로그로 확인합니다.

사례 Day 8

§4-5

분석 전에 로그 무결성을 확인합니다

SD 카드 쓰기가 밀리면 샘플이 조용히 빠집니다. 빠진 구간을 건너뛴 정착시간은 실제보다 짧게 나옵니다. tools/check_log.py 로 샘플 수와 간격을 먼저 봅니다.

사례 Day 10

§4-6

시뮬레이터의 「n = 3」 은 복제가 아닙니다

같은 설정을 세 번 돌리면 sd = 0 이 나옵니다. 그것은 확증이 아니라 동어반복입니다. 잡음 seed · 초기 위치 · 외란 시점을 바꾸고, 큰 교란을 준 대조 실행으로 그 방법이 차이를 감지하는지도 보입니다.

사례 Day 7

§5-4

PASS 는 피시험 코드가 돌았을 때만 의미가 있습니다

공이 처음부터 가운데 정지해 있으면, 제어기가 꺼져 있어도 「±5 mm 유지」 는 통과합니다. 루프 tick, 구동 명령 변화, 외란 주입 후 FAIL 여부를 시험의 전제로 검사합니다.

사례 Day 2

§5-5

raw → 물리량 변환은 한 곳에

주 루프는 보정표를 쓰는데 안전 검사만 따로 만든 근사식을 쓰면, 빔 끝에서 두 값이 어긋나 한계 검사가 통과해 버립니다. 변환 경로를 모두 찾아 하나로 모으고, 전 범위를 스윕해 확인합니다.

사례 Day 3

§5-6

설정 비교는 필드 단위로

새 필드 하나가 추가되면 해시 비교는 전부 「다름」 이 됩니다. 필드 단위로 보면 무엇이 같고 무엇이 다른지 보입니다. 차이를 지우려고 참조 데이터를 다시 만들지 않습니다 — 참조는 보고서 수치의 출처입니다.

사례 Day 12

§5-7

「없다」 고 쓰기 전에 원본과 양성 대조

PDF 에서 추출한 텍스트에 없다는 것은 원본에 없다는 뜻이 아닙니다 (표가 이미지일 수 있습니다). 그 자료에 있다고 이미 아는 값이 추출본에서 검색되는지 먼저 봅니다.

사례 Day 17

§5-8

정정도 다른 경로로 검증합니다

고치는 과정에서 새 오류가 생깁니다. 표만 고치고 요약의 수치는 그대로 두거나, 옳은 문장을 틀렸다고 「정정」 합니다. 혼자 하는 프로젝트에서도 고친 세션과 다른 경로 — 새 세션, 다른 도구, 렌더 결과 비교, 지도교수나 조교의 피드백 — 로 다시 봅니다.

사례 Day 22

§6-1

회의록에 내 프롬프트를 전부 원문으로 남깁니다

세션 종료 때 에이전트가 회의록을 쓰면서 그 세션의 프롬프트를 시각과 함께 전부 옮깁니다. 「진행」 한 마디도 빼지 않습니다. 이 기록이 있어야 나중에 「내가 논의를 어떻게 끌어갔나」 를 분석할 수 있습니다.

과목 규칙

§3규칙을 키우는 법

규칙 파일은 착수 때 완성되지 않습니다. 템플릿 (r0) 에서 시작해 프로젝트를 하며 자랍니다. 순서는 이렇습니다.

  1. 사고를 기록합니다. 회의록에 「⚠ 사고 —」 항목으로 첫 이상 1 건의 경과를 적습니다.
  2. 규칙 후보를 적습니다. 같은 회의록의 「규칙 개정 후보」 에 한 줄로 적습니다. 아직 규칙 파일을 고치지 않습니다.
  3. 학생이 결정합니다. 승격 여부는 학생 본인이 정합니다. 후보는 일주일에 한 번 승격하거나 버립니다 — 쌓아 두면 아무도 읽지 않습니다.
  4. 단독 커밋으로 고칩니다. rules: ... 커밋 하나에 규칙 변경만 담고, §9 개정 이력에 계기와 회의록 경로를 적습니다.
  5. 적재를 확인합니다. 새 세션에서 바뀐 조항을 묻습니다 (양성 대조).
계기예규칙 파일에 넣나
사고로그 샘플 누락으로 정착시간 오판넣습니다. 조항 끝에 사례 (회의록) 를 답니다
지시지도교수 면담: 「손으로 미는 외란은 비교에 쓰지 않는다」넣습니다. 결정자와 날짜를 §9 에 적습니다
기록 갱신현재 정착시간 1.2 s → 0.9 s넣지 않습니다. 수치는 실험 기록에 둡니다. 규칙 파일에 수치가 있으면 바뀔 때마다 규칙 개정이 생깁니다

규칙만으로는 재발이 멈추지 않습니다

규칙이 있어도 같은 위반은 다시 일어납니다. 반복되는 위반은 규칙 문장을 늘리는 대신 검사 도구로 바꿉니다 — 로그 무결성은 check_log.py, 시험의 전제는 smoke 스크립트의 exit 1, 세션 종료 절차는 /session-close 명령과 hook 처럼.

§4조항 하나를 쓰는 형식

N. **<규칙 이름 — 행동으로>**: <무엇을 합니다 / 하지 않습니다, 한두 문장>.
   <왜 — 어긴 경우에 무슨 일이 생기나> *(사례: YYYY-MM-DD 회의록 경로)*
  • 행동으로 씁니다. 「주의합니다」 가 아니라 「check_log.py 를 통과한 로그만 분석합니다」.
  • 측정하지 않은 주장을 넣지 않습니다. 「잡음은 항상 정착을 늦춘다」 같은 문장은 규칙의 근거가 될 수 없습니다. 실제로 재 보면 방향이 갈리기도 합니다 (사례 Day 7).
  • 이식한 규칙에는 적용 범위를 적습니다. 지난 학기의 규칙이 이번 장치에도 맞는지는 따로 확인합니다.

§5크기 관리

  • 150 행 안팎을 넘기지 않습니다. 도구마다 읽는 분량에 한도가 있고 (예: Codex 32 KiB, Claude Code 권장 200 행), 길어질수록 에이전트가 덜 지킵니다.
  • 절차서는 따로 둡니다. 보고서 작성법은 docs/writing-guide.md, 주제별 상세는 docs/ 에 두고 필요한 세션에서 읽힙니다.
  • handoff 가 두 번째 규칙 파일이 되지 않게 합니다. handoff 의 「환경 유의」 에 같은 당부가 세 번 나오면 규칙 후보로 올립니다.
